# Exhaustive structured extraction: from RAG to a loop that reads every document

Generated by `scripts/extract_structured_findings.py`, using
`scripts/rag_utils.py`'s grounding-verification helpers. This is the fix for
the failure named at the end of `insight_exploration.md`: plain top-k vector
search can't "count every instance of X" or "guarantee balanced coverage
across categories." This script doesn't ask the corpus a question and hope
retrieval touches every document -- it iterates the full 57-report manifest
explicitly, pulls every indexed chunk per report via a `report_id` metadata
filter, and asks Nova Lite to extract five fixed fields per report. That
loop-with-a-tool-call pattern is the "agent" half of this project, distinct
from the "RAG" half already covered in the first two articles.

## A real bug the gate caught

The first full run processed 56/57 reports; `M19A0090` came back with **zero
chunks retrieved**. Investigated rather than silently skipped or retried:

- The document's own status in `list-knowledge-base-documents` said
  `INDEXED` -- true, but misleading. Document-level status only confirms the
  text was chunked and embedded, not that its metadata attributes attached
  correctly.
- An unfiltered semantic query for content specific to this report (its
  vessel name and location) found it immediately, top result, score 0.88 --
  the chunk exists and is searchable.
- But that same chunk's `report_id` metadata field came back `None`. Every
  other document's `report_id` attached correctly; this one document's
  metadata write silently failed at some point across the three ingestion
  jobs this corpus went through (`infra/README.md` shows one earlier job
  with `numberOfDocumentsFailed: 1` out of 57 scanned -- this is that
  failure, previously unattributed to a specific document).

**Fix**: re-uploaded the (already-correct) metadata sidecar file and
triggered `start-ingestion-job` again. The resync's stats confirmed the
diagnosis exactly: `numberOfMetadataDocumentsModified: 1`. A second retrieve
with the same filter returned 3 chunks. Full 57-report extraction re-run
clean: 0 retrieval failures, 0 JSON parse failures.

**Why this matters more than the bug itself**: this is the second
citation/grounding failure mode this project has found (the first was
`retrieve_and_generate` returning fluent prose with zero citations). Both
share the same shape -- a status signal that looks fine (`INDEXED`, or a
fluent generated answer) while the actual grounding underneath is broken or
absent. Neither failure is visible without deliberately checking the thing
that actually matters (chunk count for a filter, citation count for an
answer) instead of the thing that's easy to check (job status, prose
fluency).

## The headline finding: 22 of 57 reports (39%) cite an unimplemented prior recommendation

This is the number the corpus-exploration document could only gesture at
qualitatively ("6 distinct reports" surfaced by one semantic query). Because
this pass touches every document, not whichever ones a query happens to
retrieve, the count is exhaustive and exact:

| Mode | Reports | Cite unimplemented prior recommendation |
|---|---|---|
| Rail | 16 | 6 |
| Pipeline | 8 | 2 |
| Marine | 18 | 9 |
| Aviation | 15 | 5 |
| **Total** | **57** | **22 (39%)** |

Four in ten investigations in this corpus point to a risk TSB (or another
body) had already flagged, that hadn't been acted on by the time the next
occurrence happened. That's a "cost of inaction" story with an exhaustive
denominator behind it, not an anecdote.

## The fatality picture is sharper than the earlier manifest-based guess

`insight_exploration.md`'s earlier pass (counting `occurrence_type` /
`notes` text in the manifest, not extracted fatality figures) suggested
marine dominated fatalities in this corpus. The exhaustive, per-report
extracted count tells a more precise story:

| Mode | Reports | Total fatalities (extracted) | Largest single report | Total excl. that report |
|---|---|---|---|---|
| Aviation | 15 | 243 | A98H0003 (MD-11, 224) | 19 |
| Rail | 16 | 55 | R13D0054 (Lac-Mégantic, 47) | 8 |
| Marine | 18 | 28 | M15P0347 (6) | 22 |
| Pipeline | 8 | 0 | -- | 0 |

**Corrected finding**: aviation and rail's totals are each dominated by one
catastrophic outlier -- remove it and both drop by roughly 85-90%. Marine's
28 fatalities are spread across the corpus instead: most of its 18 reports
carry 1-6 deaths each, with no single event responsible for the bulk of the
toll. The regulator-relevant reading isn't "which mode has the biggest
number" (aviation and rail, driven by singular disasters that already get
sustained attention) -- it's that marine's fatality burden is chronic and
distributed, the kind of pattern that's easy to under-prioritize precisely
because no single event in it is large enough to dominate headlines the way
Lac-Mégantic or Swissair 111 do. This correction -- specific numbers
overturning a plausible-sounding earlier guess -- is itself worth keeping:
it's exactly the gap between "a manifest field mentions a fatality" and "an
LLM read the actual report and extracted how many," and it's why this
extraction pass is a genuine capability upgrade, not just a bigger version
of the earlier query.

Caveat carried over honestly: this is still a hand-curated 57-report
sample, not the full 526+1,896-report population -- these are real,
per-document numbers, but they describe this corpus, not necessarily TSB's
full base rate. Extracted fatality counts are also model output, not a
verified ground truth for every entry; the multi-fatality events with public
records (Lac-Mégantic 47, Swissair 111 224/229) were spot-checked and matched
or were within one person of the known count -- individual mid-range numbers
(1-7) were not independently re-verified against source text one by one.
